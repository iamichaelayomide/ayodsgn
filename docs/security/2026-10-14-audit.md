# Life / Ramble security review — 14 October 2026

Status: source audit and isolated tests completed; hardening changes are local and NOT deployed. Production baseline: ac5b79cd93fa63cc48db2ea889a0dd73e9677c9e. This is not a certification or a forensic investigation.

## Scope and method

Reviewed the planner API dispatch, cookie/session lifecycle, persistent login, account creation and linking, account/workspace ownership, partner permissions, CSRF, mutation transactions, attachments and exports, history, AI routes/native voice command authorization, Google OAuth/token encryption/sync, push endpoints, public quotas, PWA caching and Apache routing. Inspected current tracked files for Google API-key, GitHub-token and private-key patterns without printing candidate secrets.

Tests used disposable SQLite databases and PHP 8.3 WASM, not production data. Google and AI provider tests use simulated transports. No brute force, live mutation, real private record download, microphone recording or external messaging was performed.

## Confirmed findings and local changes

### S1 — Medium: a revoked device login did not revoke all sessions derived from it

A remembered cookie can legitimately recreate multiple PHP sessions. Logout deleted the device row and the current PHP session, but an earlier authenticated session still had valid account credentials. Its next request could issue a new device cookie, effectively undoing device logout.

Added LifeRemember::validSession: a session carrying rememberId must still reference a live, unexpired, identity-matching device row whose credential fingerprint matches. The API checks this before keeping the device logged in or dispatching any authenticated action. A revoked derived session becomes anonymous, its cookie is cleared and it cannot mint another login. Separately authorized devices remain active; older sessions without rememberId still acquire the existing persistent login normally.

Evidence: two real isolated API sessions created from one device login; after logout, replay of the earlier session plus the old cookie is denied. Unit tests also cover account mismatch, expiry and independent devices.

Residual limitation: this is revocation, not protection against malware stealing an active bearer cookie before logout. Persistent login remains the requested one-year rolling lifetime. A stolen token remains usable until expiry, credential change or device revocation. There is no user-facing device inventory/revoke-all screen.

### S2 — Low: request-size check relied solely on the declared length

The JSON route trusted CONTENT_LENGTH before reading php://input. Added a bounded read of 150,001 bytes and rejection over 150,000 bytes, including a missing or misleading length. This bounds application decoding; upstream request buffering must still have appropriate hosting limits.

Evidence: an isolated API POST with oversized actual JSON and CONTENT_LENGTH=0 returns 413; missing CSRF remains 403.

### S3 — Low: legacy password creation silently permitted bcrypt truncation

Legacy owner setup, partner acceptance and recovery allowed 200-byte passphrases while PHP's bcrypt only uses the first 72 bytes. Email account creation already enforced the 72-byte bound. New legacy passwords now reject values above 72 bytes and NUL bytes rather than truncating them.

Existing hashes and sign-in compatibility are preserved. An existing legacy password created above 72 bytes still needs a deliberate password reset: its discarded suffix cannot be recovered from the hash. No production password was changed.

Reference: https://www.php.net/manual/en/function.password-hash.php (bcrypt's 72-byte limitation).

### S4 — Preventive hardening: deployment includes files that are not public application routes

Added root web rules denying tests/, scripts/, docs/, hidden paths except .well-known, and SQL/SQLite/backup/log/private-key extensions; disabled directory listing. Existing maintenance PHP scripts already have CLI-only guards. These rules prevent direct execution of test fixtures and accidental publication of operational files if the full repository is deployed.

Exposure through the production origin was not established: all automated public requests, including the homepage, returned the same protection-layer 403. The new Apache rules need live verification after deployment. This is hardening, not a claim that private server files were exposed.

### S5 — High advisory severity: vulnerable image-processing development dependency

The approved npm registry scan checked 52 locked package names/versions and returned two high-severity advisories for sharp 0.35.3:

- GHSA-rgj7-g3m4-5g8c: vulnerable libheif dependencies; sharp versions below 0.35.4 are affected. https://github.com/advisories/GHSA-rgj7-g3m4-5g8c
- GHSA-wq5f-xc86-pv6w: vulnerable librsvg dependency; sharp versions below 0.35.5 are affected. https://github.com/advisories/GHSA-wq5f-xc86-pv6w

Updated package.json to sharp ^0.35.5 and regenerated package-lock.json using the official npm resolver, with dependency lifecycle scripts disabled. Related native binaries and libvips packages changed with the patched dependency tree. The follow-up npm audit reports zero known vulnerabilities in that lockfile.

Exposure is bounded by actual use: sharp is a development dependency used by the portfolio media optimization script. The Life PHP upload route does not invoke it. No direct live-planner exploit or compromise was demonstrated. Processing attacker-supplied images in development/build environments still warrants the update. Private installed PHP dependencies and the separately vendored browser editor are not covered by this npm result.

Verification: an isolated installation of sharp 0.35.5 successfully created a PNG, decoded it, resized it and encoded/read a WebP. The existing site validator passed in a temporary snapshot containing files omitted by this sparse checkout. Initial validation in the partial working folder failed only because required portfolio files were omitted, not because the security change removed them. No media files were regenerated or published.

Evidence files: npm-advisories-2026-10-14.json (initial registry findings), npm-audit-after-2026-10-14.json (official npm audit after the fix). Temporary tooling was checksum-verified against npm's published integrity and kept outside the repository.

## Remaining risks and follow-up work

1. **Medium — email ownership is not verified.** Anyone can register an unused address they do not control. Server-side linking correctly refuses automatic merging by email, so this review did not demonstrate access to another user's existing planner. However, address pre-registration and account recovery/identity trust remain concerns. Implement expiring, single-use verification tokens and a verified state before treating email as identity; do not retroactively lock out existing users without a migration plan.
2. **Availability — global login threshold.** The legacy/Google-start throttle blocks all callers after 30 attempts in 15 minutes. A distributed attacker could exhaust that shared bucket. Per-address/account limits and hosting-level abuse controls should replace or complement the shared limit; simply removing it would weaken brute-force protection. Existing email login has separate IP and email buckets. Concurrent rate-limit races and production edge protections were not load-tested.
3. **Lifecycle — persistent devices and push notifications.** Provide a device list and revoke-all operation. Logout currently unsubscribes device push through the browser and server client flow; browser failure or an interrupted flow may leave a subscription. Subscription IDs are account-scoped, and endpoint origins are allowlisted. Stronger server-side association of push subscriptions to login devices would make logout cleanup authoritative.
4. **Hosting/dependencies — not verified.** Inspect the actual private Composer lockfiles (Google client and push libraries), installed PHP/OS patch levels, TLS/HSTS, filesystem permissions, backups/retention and deployment account permissions. The local npm lockfile has now been scanned and patched; it describes build tools, not the complete deployed PHP dependency tree. Do not equate absence of obvious source flaws or advisory search results with absence of vulnerable dependencies.
5. **AI trust boundaries.** Scoped tools, target validation, transaction/read-back receipts and restrictions on destructive/external actions are present and exercised. Model-mediated instruction checks remain heuristic; no claim of universal prompt-injection resistance is made. Real provider adversarial sessions and microphone behavior are not covered by deterministic tests.
6. **Secret history.** Current tracked files had zero matches for the scanned high-confidence credential patterns. Full Git history, private server settings, CI secrets, untracked outputs and provider dashboards have not been exhaustively scanned. No automatic credential rotation is justified by these checks alone.

Verify normal login, remembered reopen, multi-session logout revocation, canonical redirects, public PWA assets and /.well-known/ access; confirm /tests/, /scripts/, /.git/config and schema files are denied at the origin. Verify actual private files are outside the web root and remain inaccessible.
